# Running SUPRA-Tex on AMD Instinct MI300X

The released single-image Qwen pipeline runs on one gfx942 GPU under Linux. It uses ROCm for geometry generation, neighborhood attention, material prediction, sparse completion, mesh processing and texture sampling. The UV coverage raster uses headless Mesa EGL. This avoids a device fault in the HIP rasterizer's triangle-binning kernel on the tested DigitalOcean MI300X VF.

## Install

Use the ROCm 7.2.4 image with Python 3.12 and PyTorch 2.9.1. From a SUPRA-Tex checkout on the host, create a persistent native build directory and start a container with access to the GPU.

```bash
native_dir="${PWD}-rocm-native"
mkdir -p "$native_dir"
docker run -dit --name supra-mi300 \
  --device=/dev/kfd --device=/dev/dri --shm-size=32g \
  -v "$PWD:/work/SUPRA-Tex" -v "$native_dir:/work/native" -w /work/SUPRA-Tex \
  rocm/pytorch@sha256:7fe531fa185af260352fe7fbb3fa64ad749abe72adf0600a648c4692801b125a \
  sleep infinity
docker exec supra-mi300 bash deployment/runtime/rocm/install.sh /work/native
```

The installer builds four native extensions, installs AMD AITER, and places the native source directories on the container's Python path. Keep those directories mounted when using the container. The CPU voxelizer uses OpenMP and a dense hash table for the triangle-to-voxel lookup. Source revisions and the complete voxelizer patch are in [the ROCm installer](../deployment/runtime/rocm/install.sh).

Prepare models with the usual command inside the container. The geometry model uses the gated DINOv3 weights. When using existing model directories, mount them at stable paths and pass the corresponding local overrides. The default example supplies foreground alpha. For opaque RGB inputs, pass an approved RMBG model or the supported public BiRefNet override during preparation. [Model preparation](weights.md)

```bash
docker exec -it supra-mi300 python scripts/prepare_models.py
docker exec supra-mi300 python scripts/check_runtime.py --config ckpts/ready/models.json
docker exec -e OMP_NUM_THREADS=10 -e OPENBLAS_NUM_THREADS=1 supra-mi300 \
  python scripts/run_example.py --output /work/SUPRA-Tex/shell.glb
```

## Single-image scheduling

With at least 128 GiB free on one MI300X, the high-memory Qwen frontend overlaps its geometry and material subprocesses on that card. They share the prepared photograph and publish separate outputs. The frontend waits for both before starting completion. Use `--no-parallel-frontend` to run them sequentially. The low-VRAM path keeps its serial default.

## Completion attention

On gfx942 with AITER installed, inference uses the BF16 assembly kernel for unmasked single-sequence BF16 attention with head dimension 128. PyTorch SDPA handles other shapes and training. The run receipt records the MI300X mode. Qwen's spatial VAE uses channels-last convolution weights to avoid layout conversions in MIOpen.

| Selection | Behavior |
| --- | --- |
| Default | BF16 AITER for eligible completion attention, or SDPA when AITER is unavailable |
| `--attention sdpa` | PyTorch SDPA throughout completion |
| `SUPRATEX_MI300_ATTENTION=fp8` with automatic attention | Quantize Q, K and V per tensor to E4M3 FNUZ, use AITER FP8 attention and return BF16 |

BF16 is the default for material accuracy. On two 25-step, eight-view courtyard fields with identical 2D inputs and the on-device A100-compatible noise mode, the largest per-channel mean absolute error against A100 BF16 was 0.25 out of 255. FP8 trades material fidelity for speed. MI300X completion defaults to the A100 release's seeded Philox sequence. The ROCm kernel generates it for the requested seed and token count. On the two validation shapes, its maximum absolute difference from CUDA's float32 starting tensor was 0.0000024. Set `SUPRATEX_MI300_NOISE=native` to use PyTorch's ROCm device generator instead. This setting affects the completion starting field. Geometry and 2D map prediction retain their own seed handling.

## Profiling

For reproducible timing, make a warmup pass for the target shapes so FlexGEMM and MIOpen can cache their kernel choices. Record model loading, CPU grid construction, sampling, field publication and GLB export separately when comparing workloads. These profiling tools can run inside the container. For native CPU sampling in Docker, start it with `--cap-add SYS_PTRACE --security-opt seccomp=unconfined`.

```bash
rocprofv3 --kernel-trace --memory-copy-trace --stats -f csv -d trace -- python scripts/run_example.py --output profile.glb
py-spy record --native --subprocesses --format speedscope -o cpu.json -- python scripts/run_example.py --output cpu-profile.glb
```

Install `py-spy` in the container before using the CPU command. Each command needs a new output filename.
